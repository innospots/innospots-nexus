# 企业级 AI 开发与生产平台

## 修订版架构设计及三阶段开发计划

**文档版本：** 3.2
**状态：** 提议 / 开发基线  
**目的：** 在 2.0 合约与运行时基线上，将平台收束为基于 pi 的可扩展智能体框架，并形成覆盖导航、标签页、主页面、右侧看板和设置区的完整应用体验。

### 相对 2.0 的核心调整

1. **智能体框架优先于功能清单。** 平台提供可扩展的能力宿主。Agent、Tool、MCP 都以功能扩展形式接入。
2. **体验层覆盖完整的应用使用过程。** 体验层不仅包含应用构建，还承载 AI 对话、应用页面、应用展示和定制化应用嵌入。
3. **控制面采用可伸缩工作台。** 工作台由左侧功能区、顶部多标签页、主页面区、右侧看板和设置区组成，各区域按当前内容动态展开或收起。
4. **导航采用声明式配置。** 平台导航与扩展导航遵循同一配置机制，调整菜单和页面入口不需要修改控制面内核；本文只说明机制，不定义 YAML 结构。
5. **页面以标签页承载。** 从左侧功能区打开不同功能时，在主区域顶部创建或切换对应标签页，每个标签页对应一个独立页面上下文。
6. **右侧看板可扩展。** 右上角提供侧边看板入口，扩展可以贡献看板内容；打开看板时工作区智能收缩，关闭后释放空间并恢复左侧功能区。
7. **设置区按宿主与扩展分层。** 设置区拥有自己的设置菜单和以表单为主的设置页面；基础设置包含模型与扩展，其他设置由功能扩展贡献。
8. **数据归属双边界。** Workspace 与 Project 都是数据归属边界，但 Workspace 不对客户开发开放，只对管理开放；客户开发者只面对 Project。

# 1. 执行摘要

平台战略方向不变：以 pi 作为智能体执行的基础框架，由平台拥有领域模型、执行约束和运行时边界；第三方能力以统一扩展形式接入，并将 AI 或人类生成的可持久化数字成果作为一等生产对象。

3.2 在此之上补全扩展骨架、应用体验与执行标准：

> **基于 pi 的可扩展智能体框架 + 完整应用体验层 + 可伸缩工作台 + 不可变执行快照 + 以数字成果为中心的生产。**

实施约束仍然成立：

1. **不要并行构建所有领域。** 首个发布证明完整闭环：安装扩展 -> 从左侧功能区打开标签页 -> 对话或使用应用页面 -> 基于 pi 执行 -> 生成数字成果 -> 预览/编辑/版本化 -> 复用。
2. **DSL 用于约束执行，而不是成为用户界面的负担。** 平台以标准 YAML DSL 描述执行内容、资源绑定和执行约束，但本文不展开其结构、字段或语法标准。
3. **pi 是基础执行框架，平台仍拥有执行标准。** Agent 在 pi 上运行，平台负责把 DSL 定义编译为稳定、可审计的执行快照。
4. **不要仅将数字成果视为文件存储。** 数字成果需要版本、血缘、预览、编辑和转换能力。
5. **控制面配置与运行时执行分离。** 运行时执行不可变 Run/Execution 快照。
6. **能力隔离从第一天开始。** 可安装扩展即是代码边界，需要清单、权限、密钥、沙箱和信任策略。
7. **暂缓公开市场。** 先私有/内部注册表与安装器。
8. **不要把 Workspace 暴露给客户开发。** 客户开发入口是 Project；Workspace 是管理侧归属与隔离边界。

# 2. 修订版架构原则

## 2.1 核心原则

| 原则           | 决策                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------- |
| 框架策略       | 平台是可扩展的智能体宿主，不是预置功能清单。                                                 |
| 扩展策略       | Agent、Tool、MCP、页面、导航、查看器均通过 Capability / Extension 合约进入。                 |
| 体验策略       | 体验层统一承载 AI 对话、应用页面、应用展示、定制化应用嵌入及各 Studio 能力。                  |
| 控制面策略     | 控制面由左侧功能区、顶部标签页、主页面区、右侧看板和设置区构成，并支持空间自适应。            |
| 导航策略       | 左侧导航采用声明式配置，平台与扩展贡献统一合并、鉴权和渲染。                                 |
| 设置策略       | 设置区拥有独立菜单和表单型页面；基础设置为模型与扩展，其他设置由扩展贡献。                   |
| 数据策略       | Workspace 与 Project 都是归属边界；Workspace 仅管理可见，Project 是客户开发边界。            |
| 领域所有权     | AI 对象模型、数字成果、Agent 清单、运行时合约和策略模型由平台拥有。                          |
| 运行时策略     | Agent 基于 pi 执行；平台通过标准 YAML DSL 给出执行定义和约束。                               |
| 执行策略       | 控制面将配置编译为不可变的 Run/Execution 快照。                                              |
| 数字成果策略   | 数字成果是一等对象，而非聊天响应的副作用。                                                   |
| 安全策略       | 能力、权限、密钥、沙箱和网络控制是运行时的显式关注点。                                       |
| 存储策略       | 元数据在 PostgreSQL；大容量内容在对象存储；遥测与事务数据分离。                              |
| 开发策略       | 三个阶段：控制面闭环 -> 平台化 -> 生态系统与企业级。                                         |

# 4. 体验层与控制面

## 4.1 应用体验层

体验层回答「用户如何使用 AI 和应用」。AI Studio、Agent Studio、数字成果工作区与 App Studio 仍是平台的能力入口，但最终体验不局限于 Studio 内部，而是统一落到四种可组合的使用形态。

| 使用形态       | 用户体验                                                         | 典型来源                     |
| -------------- | ---------------------------------------------------------------- | ---------------------------- |
| AI 对话        | 通过自然语言持续交互，查看流式回答、工具过程和数字成果            | AI Studio、Agent Studio      |
| 应用页面       | 在完整页面中完成查询、编辑、审批、分析和业务操作                  | App Studio、扩展页面         |
| 应用展示       | 以面板、报告、仪表盘、数字成果预览或演示模式呈现结果              | 数字成果工作区、应用扩展     |
| 定制应用嵌入   | 将外部或专用应用安全嵌入工作台，并继承项目上下文、权限和主题      | 企业应用、第三方应用、插件页 |

同一个应用可以同时提供对话、页面和展示能力。例如，用户在 AI 对话中发起分析，在新的标签页中打开结果页面，并在右侧看板查看运行状态或辅助信息。

### AI Studio 的交互式应用模式

AI Studio 以交互对话为主要应用模式，并提供以下能力：

- 为对话增加一个或多个技能，使 Agent 能够调用特定领域能力；
- 指定当前 Project，使模型、知识、工具、权限和数字成果都在明确的项目边界内运行；
- 配置对话的展示方式与视觉效果，包括欢迎页、消息卡片、数字成果卡片和应用唤起方式；
- 调试对话交互，查看模型请求、上下文装配、工具调用、技能执行、运行事件、耗时、错误及原始消息明细；
- 从对话中打开应用页面或数字成果页面，并保持会话与页面之间的关联。

面向普通用户时只展示必要的交互结果；调试消息明细仅在开发或诊断模式下打开，避免技术信息干扰正式应用体验。

## 4.2 控制面形态：可伸缩工作台

控制面回答「如何进入、配置、运行和查看」。领域操作统一挂在一个可伸缩工作台中，而不是拆成互不相通的资源后台。

```text
+--------------------------------------------------------------------------------+
| 顶栏：当前 Project / 全局操作                         右侧看板入口 / 用户      |
+----------------+------------------------------------------------+--------------+
| 左侧功能区     | 顶部标签页                                     | 右侧看板     |
|                +------------------------------------------------+              |
| 平台菜单       |                                                | 扩展面板     |
| 扩展菜单       | 主页面区                                       | 状态/辅助信息|
| 设置入口       | 对话 / 应用页面 / 应用展示 / 定制化嵌入        |              |
+----------------+------------------------------------------------+--------------+
```

| 区域           | 职责                                                                 |
| -------------- | -------------------------------------------------------------------- |
| 左侧功能区     | 展示平台菜单与扩展菜单，负责打开功能页面，并提供设置入口             |
| 顶部标签页     | 保存已打开页面；不同标签对应不同页面及其独立状态，可切换和关闭       |
| 主页面区       | 承载 AI 对话、应用页面、应用展示、数字成果以及定制化嵌入             |
| 右侧扩展看板   | 由右上角入口打开，承载运行状态、上下文信息、辅助工具和扩展贡献内容   |
| 设置区         | 提供独立设置菜单与以表单为主的配置页面                               |

### 自适应伸缩规则

- 主页面内容较大时，左侧功能区可以收起为窄栏或图标栏，为页面释放横向空间；
- 打开右侧看板时，布局根据主页面的最小可用宽度决定是压缩左侧功能区、覆盖显示看板还是进入聚焦模式；
- 关闭右侧看板后，释放的空间优先归还主页面，并允许左侧功能区恢复到用户关闭前的展开状态；
- 用户手动选择的展开或收起状态应被记忆，智能伸缩只做临时布局调整，不覆盖用户偏好；
- 对话、表格、画布、预览和嵌入应用可以声明不同的最小显示宽度，由工作台统一完成空间协调。

## 4.3 左侧功能区与顶部标签页

平台默认菜单和扩展贡献菜单采用同一套声明式配置机制。控制面在启动或扩展状态变化时合并菜单，完成权限过滤、分组、排序和可见性判断。本文不规定 YAML 字段、结构或配置标准。

菜单项打开页面时遵循以下行为：

1. 未打开过的功能创建新标签页，并加载对应页面；
2. 已打开的同一页面默认切换到原标签，需并行处理多个对象时可显式创建新实例；
3. 标签保存页面标识、标题、图标、项目上下文和必要的恢复状态；
4. 关闭标签只销毁当前页面会话，不影响该功能在左侧菜单中的入口；
5. 扩展只能贡献被授权的菜单与页面，不能覆盖平台核心入口；
6. 设置入口固定可达，但具体设置菜单可以随已启用扩展动态增减。

阶段 1 提供稳定的多标签基础能力，不追求完整 IDE 式窗口系统；分屏、拖拽重排和跨窗口恢复可在后续阶段增强。

## 4.4 主页面与右侧扩展看板

主页面由当前标签页决定，可以承载对话、普通应用页面、应用展示、数字成果页面或定制化嵌入应用。页面由平台 Studio 或扩展贡献，不在控制面内核中写死具体业务路由。

右侧扩展看板是独立贡献点。运行状态、对话上下文、调试信息、数字成果属性、页面帮助和第三方辅助工具都可以注册为看板。右上角只展示当前页面可用且用户有权访问的看板入口；点击后在右侧打开，再次点击或主动关闭后收起。

看板与主页面共享当前 Project、标签页和选中对象的上下文，但不能直接修改其他页面的私有状态。需要产生业务变更时，应通过平台能力或页面公开动作完成，以保持权限、审计和错误处理一致。

## 4.5 设置区

设置区是可扩展的配置应用，不是第五个 Studio。它由左侧设置菜单和设置主页面组成，主页面以表单为主，也可以在确有需要时提供连接测试、权限确认、扩展安装和状态说明。

设置菜单分为两层：

- 基础设置：模型与扩展。模型负责提供者、默认模型和当前 Project 绑定；扩展负责安装、启用、停用和扩展级配置；
- 功能扩展设置：由已启用扩展按能力贡献，例如 Agent、Tools、MCP、应用、数字成果查看器或企业集成。

Agent、Tools、MCP 不作为与模型并列的固定基础分类。只有相应扩展已安装、已启用且当前用户有权限时，其设置菜单和表单才出现。扩展定义配置含义和校验要求，设置宿主统一提供表单布局、敏感字段保护、保存、校验、错误提示和审计。

# 5. 可扩展功能体系

智能体框架的产品含义是：平台先提供宿主，再通过扩展生长功能。

## 5.1 宿主与贡献点

```text
智能体框架（Host）
  ├── 扩展生命周期   发现 / 安装 / 启用 / 配置 / 停用
  ├── 能力路由       CapabilityRegistry / CapabilityRouter
  ├── 运行时合约     AgentRuntime / ToolRuntime
  ├── 控制面贡献点   菜单 / 页面 / 对话卡片 / 设置 / 右侧看板
  └── 安全贡献点     能力声明 / 权限审查 / 密钥
```

这与 `innospots-nexus-core` 已有的 Plugin / Capability 模型对齐：

- `PluginDefinition`：扩展静态声明
- `CapabilityContribution`：扩展提供的能力
- `CapabilityRouter`：按类型与标签选择实现
- `ConfigDefinition`：扩展配置描述，用于驱动设置区表单

AI 平台不另起一套插件内核，而是在该宿主上定义 AI 领域的能力类型。

## 5.2 能力类型

阶段 1 先冻结这些能力名：

| Capability            | 谁提供           | 控制面如何消费                         |
| --------------------- | ---------------- | -------------------------------------- |
| `model.provider`      | 模型扩展         | 基础设置-模型；运行时模型调用          |
| `agent.runtime`       | Agent 扩展       | AI 对话选择 Agent；Run 执行            |
| `tool.invoke`         | Tool 扩展        | Agent 调用；设置区 Tools               |
| `mcp.server`          | MCP 扩展         | 作为 Tool 来源接入；设置区 MCP         |
| `artifact.viewer`     | 查看器扩展       | 主页面预览数字成果                     |
| `artifact.editor`     | 编辑器扩展       | 主页面编辑数字成果                     |
| `control.nav`         | 任意扩展         | 合并到左侧导航                         |
| `control.page`        | 任意扩展         | 主页面路由                             |
| `settings.section`    | 任意扩展         | 设置区功能扩展段                       |
| `control.sidepanel`   | 任意扩展         | 右侧扩展看板                           |

Agent、Tools、MCP 的共同身份是 **功能扩展**：同一安装、启用、配置、权限审查流程，不同的 Capability 合同。

## 5.3 统一扩展定义

系统采用统一的、类似插件的扩展形式增加能力。一个扩展可以声明自身提供的能力，并按需贡献菜单、标签页页面、右侧看板、设置表单、对话卡片、接口、运行时适配器、工具或数字成果查看器。平台使用同一套发现、安装、启用、配置、停用、升级和审计流程管理这些扩展。

扩展定义至少表达以下语义，但本文不提供 YAML 结构或字段标准：

- 扩展身份、版本、兼容范围和依赖关系；
- 对外提供的能力，以及这些能力可被哪些页面或运行时消费；
- 对控制面的菜单、页面、看板和设置贡献；
- 对服务端接口、Agent、Tool、MCP、模型或数字成果处理能力的贡献；
- 运行所需的网络、文件、密钥、模型、工具和数据访问权限；
- 安装、启用和升级时需要执行的校验与迁移要求。

能力与权限必须分开理解：能力描述扩展能够做什么，权限描述本次安装被允许做什么。扩展声明需要网络能力，并不代表安装后自动获得无限制网络访问。

菜单、页面和接口不拥有独立于扩展的生命周期。停用扩展时，其贡献内容同时从能力路由、控制面和接口暴露中撤销；再次启用前，平台应完成依赖、权限和兼容性检查。

## 5.4 为何把 Agent / Tool / MCP 都做成扩展

| 若做成一等内置模块     | 结果                         |
| ---------------------- | ---------------------------- |
| 设置区写死三类菜单     | 未使用的能力仍占用产品结构   |
| 控制面为每类能力做后台 | 控制面裂变成资源清单，离开统一工作台体验      |
| 安装流程各写一套       | 清单、权限、版本无法复用     |

统一为扩展后：新增一种工具、一个 MCP 服务器、一个专用 Agent，只增加扩展包，不改控制面形态，不改体验层 Studio 划分，不改设置信息架构。

# 6. 数据归属边界：Workspace 与 Project

## 6.1 层级

```text
Tenant
  └── Workspace          管理可见；隔离与治理边界
        └── Project      客户开发可见；控制面与资源归属边界
              └── 资源   Agent / Tool / MCP / 模型绑定 / 数字成果 / Run
```

与现有 Nexus 治理对齐：

- 隔离键仍然是 `tenantId` + `workspaceId`（`WorkspaceBaseEntity` / `TLC`）。
- Project 是 **AI 领域的归属容器**，不是新的 IAM 隔离键，也不替代 kernel 的 Workspace。
- 多租户治理方案中「Workspace 下不引入 Project 业务实体」约束的是 IAM；本方案的 Project 属于 AI 开发平台领域，挂在已有 Workspace 之下。

## 6.2 可见性

| 主体           | 可见 Workspace | 可见 Project | 典型操作                         |
| -------------- | :------------: | :----------: | -------------------------------- |
| 平台运营       |       是       |      是      | 租户/空间治理、审计、配额        |
| 租户管理员     |       是       |      是      | 创建空间、分配成员、查看全部项目 |
| 客户开发者     |       否       |      是      | 打开项目、对话、管理扩展与产物   |

规则：

- **Workspace 不对客户开发开放。** 开发者 API、控制面顶栏、资源路径都不出现 workspace 选择器。
- 开发者进入控制面时，上下文是当前 Project；服务端由 Project 解析出 `workspaceId` 做隔离。
- 管理端（kernel / platform 控制台）管理 Workspace，并可以按空间查看其下 Project。
- 一个 Workspace 可包含多个 Project；Project 不能跨 Workspace 移动（阶段 1）。

## 6.3 API 边界

```text
管理 API（管理员）
  /management/workspaces
  /management/workspaces/:id/projects

开发 API（客户开发者）
  /projects
  /projects/:id/extensions
  /projects/:id/models
  /projects/:id/runs
  /projects/:id/artifacts
```

开发 API 的资源路径以 Project 为根。Workspace 只出现在管理 API。

# 8. Agent 模型与第三方集成

Agent 是功能扩展的一种。安装、权限、导航贡献走统一扩展管道；执行走 Runtime Contract。

## 8.1 Agent Provider 合约

```typescript
interface AgentProvider {
  getManifest(): AgentManifest;
  validate(input: unknown): ValidationResult;
  execute(input: AgentInput, context: AgentContext): AsyncIterable<AgentEvent>;
}
```

提供者：

```text
NativeAgentProvider
PiAgentProvider
RemoteAgentProvider
MCPAgentProvider
ExternalAPIProvider
```

应用代码依赖平台的 `AgentProvider`，不直接调用 pi 的内部 API。平台以此边界统一注入项目上下文、技能、工具、模型和执行约束。

## 8.2 Tool 与 MCP

```text
Tool 扩展  --tool.invoke-->  ToolRuntime
MCP 扩展   --mcp.server-->   MCP Adapter --tool.invoke--> ToolRuntime
Agent 扩展 --agent.runtime--> AgentRuntime --调用--> ToolRuntime
```

MCP 不是第三套运行时，而是 Tool 能力的一种提供者。设置区出现 MCP，是因为用户需要配置服务器地址与授权，并不意味着 MCP 拥有独立于扩展体系的生命周期。

# 9. 运行时架构

## 9.1 Runtime Contract

平台拥有此合约：

```typescript
interface AgentRuntime {
  createRun(input: AgentRunInput): Promise<AgentRun>;
  stream(runId: string): AsyncIterable<AgentEvent>;
  resume(runId: string): Promise<AgentRun>;
  cancel(runId: string): Promise<void>;
  inspect(runId: string): Promise<AgentTrace>;
}
```

## 9.2 基于 pi 的执行基础

```text
平台执行标准与 YAML DSL
        |
        v
PiRuntimeAdapter
        |
        v
pi Agent 基础框架
```

pi 是平台 Agent 执行的基础框架。平台适配层负责把 Project 上下文、技能、工具、模型绑定、事件、取消与恢复语义映射到 pi，并隔离 pi 版本升级对上层产品能力的影响。平台拥有执行定义、权限和审计语义，pi 负责按这些约束完成具体智能体运行。

## 9.3 执行规则

运行时必须执行不可变的执行快照。快照由平台根据标准 YAML DSL 生成，固定本次运行使用的 Project、Agent、技能、模型、工具、知识、策略、输入输出和 pi 运行参数。本文只说明执行机制，不定义 YAML DSL 的结构、字段和语法标准。

正在运行的任务不得因为用户在控制面设置区编辑了扩展配置而静默改变行为。

# 10. YAML DSL 与执行约束

## 10.1 声明式执行标准

```text
Studio / 控制面 / API / 扩展
   |
   v
标准 YAML DSL
   |
   v
校验 + 解析 + 能力与权限绑定
   |
   v
ExecutionSnapshot
   |
   v
运行时
```

标准 YAML DSL 是 Agent 执行的声明式入口，用于表达运行目标、所用技能与资源、输入输出、步骤关系、权限边界和运行约束。平台将其校验并编译为不可变执行快照，再交由基于 pi 的运行时执行。

导航配置与执行 DSL 可以使用相同的 YAML 表达媒介，但二者语义和生命周期独立：导航配置决定用户能看到和打开什么，执行 DSL 决定 Agent 如何在约束内运行。本文不提供任何 YAML 示例、字段清单、结构定义或语法标准。

## 10.2 校验与编译职责

- 声明完整性验证
- 类型验证
- 依赖解析
- 版本解析
- 能力验证
- 权限验证
- 环境验证
- 运行时兼容性验证
- 快照生成

# 11. 数字成果平台

数字成果是 AI 或人类在平台中形成的可持续使用结果，也是该架构中最重要的产品差异化因素之一。

## 11.1 定义

> 数字成果是由 AI 或人类生成或修改，能够持久保存、独立访问、持续版本化、直接预览、编辑、复用和转换的数字输出，例如文档、图片、数据、代码、演示文稿或应用包。

每个数字成果属于一个 Project，管理侧可以按 Workspace 汇总。它不是对话消息中的临时附件，而是能够被应用、Agent、工作流和其他用户继续消费的业务对象。

类型系列：

```text
文档 / Markdown / HTML / 代码
图像 / 视频 / 音频
演示文稿 / 电子表格
数据集 / JSON
应用程序包
```

## 11.2 核心信息

数字成果需要记录稳定标识、所属 Project、内容类型、版本、状态和内容存储位置；同时保留来源运行、生成 Agent、父成果、转换关系及可扩展元数据，以支持追溯、审计和再次生产。

## 11.3 存储与操作

```text
数字成果元数据   -> PostgreSQL
数字成果内容     -> 对象存储
预览缓存          -> 对象存储 / 缓存

操作：创建 / 读取 / 更新 / 修补 / 快照 / 差异 / 渲染 / 导出 / 转换
```

大型二进制文件不得嵌入事务行。

## 11.4 血缘

```text
Research Agent
      |
      v
research.md
      |
      v
PPT Agent
      |
      v
presentation.pptx
```

血缘通过来源运行、父成果和转换记录查询。数字成果工作区通过主页面展示这条关系，并允许用户从任一成果回溯生成过程或继续转换。

# 12. 数字成果查看器 / 编辑器

查看器与编辑器也是扩展，通过数字成果查看与编辑能力注册到主页面。平台内部可以保留 `artifact.viewer`、`artifact.editor` 等稳定技术标识，但产品文案统一使用“数字成果”。

查看器需要声明自己支持的内容类型和版本，并把内容渲染为可展示结果；编辑器在此基础上提供编辑会话、保存新版本和冲突处理。平台负责选择匹配的扩展、校验权限、记录版本与审计信息，扩展不直接绕过数字成果服务写入底层存储。

控制面按数字成果类型选择扩展，并在独立标签页或当前页面的预览区域打开。阶段 1 内置文本、Markdown、JSON 和图片预览即可。

# 17. 三阶段开发策略

## 阶段 1 - 控制面闭环

### 目标

证明统一扩展体系、应用体验层、可伸缩工作台和基于 pi 的 Agent 执行可以端到端闭环：

> 管理侧准备 Workspace -> 开发者进入 Project -> 安装扩展并配置模型 -> 从左侧功能区打开标签页 -> 对话或使用应用页面 -> 按标准 YAML DSL 在 pi 上运行 -> 生成数字成果 -> 预览、编辑、版本化和复用

### 范围

#### 体验层

- 打通 AI 对话、应用页面和数字成果展示；定制化应用嵌入提供安全宿主
- AI Studio 支持添加技能、指定 Project、配置对话展示效果和查看调试消息明细
- AI Studio、Agent Studio、数字成果工作区和 App Studio 作为能力入口接入同一工作台

#### 控制面

- 壳：顶栏 Project 上下文、左侧功能区、顶部多标签页、主页面、右侧看板和设置区
- 声明式导航与扩展菜单贡献合并，不在本文中定义 YAML 结构
- 多标签页创建、切换、关闭和页面状态恢复
- 右侧看板入口、扩展内容加载及与左侧功能区联动的智能伸缩
- 主页面支持对话、应用页面、数字成果展示和定制化应用嵌入
- 设置区提供设置菜单、模型与扩展基础设置，以及扩展贡献的表单页面

#### 数据边界

- Workspace 管理 API（创建/列表，不进入开发控制面）
- Project 开发 API 与控制面入口
- 资源归属 Project，隔离键 `tenantId` + `workspaceId`

#### 扩展体系

- 统一扩展定义与生命周期
- 能力类型覆盖模型、Agent、Tool、MCP、菜单、页面、设置、右侧看板、接口和数字成果处理
- 私有/内部 Registry
- 安装器、依赖验证、权限审查
- Agent / Tool / MCP 均走同一安装管道

#### 运行时

- 平台 Runtime Contract 与基于 pi 的执行适配层
- 标准 YAML DSL 的最小执行子集、约束校验和不可变执行快照
- Agent Run 生命周期、流式事件、取消/恢复（支持时）
- 基础状态/会话

#### 模型与工具

- Model Provider 合约，至少两个适配器
- Native Tool 合约
- MCP Tool 适配器

#### 数字成果

- 数字成果模型、对象存储、版本化、血缘
- Markdown / JSON / 图片 / 基础文件预览
- 基础文本编辑
- 数字成果工具：创建、读取、更新和差异对比

#### 可观测性

- Run 追踪、模型/工具计时、代币/成本字段、结构化日志

### 明确不包含

- 向客户开发者暴露 Workspace
- 公开市场
- 客户侧可视化导航或 YAML DSL 编辑器
- 完整可视化 DSL 构建器
- 多引擎工作流编排
- 完整企业级 ABAC
- 高级评估平台
- 完整应用部署引擎
- 所有数字成果编辑器
- 把控制面拆回资源模块平铺后台
- 完整 IDE 式窗口、任意分屏与跨窗口布局系统

### 阶段 1 退出标准

```text
管理员创建 Workspace
        |
        v
开发者打开 Project（不见 Workspace）
        |
        v
安装 Agent / Tool / MCP 扩展
        |
        v
基础设置绑定模型
        |
        v
左侧功能区出现扩展贡献菜单
        |
        v
打开新标签页并加载对话或应用页面
        |
        v
AI Studio 指定 Project/技能 -> 标准 YAML DSL -> pi -> 工具/MCP
        |
        v
数字成果已创建并在页面中预览/编辑/版本化
        |
        v
右侧看板显示运行/调试信息，数字成果被另一个 Agent 复用
```

## 阶段 2 - 平台化

### 目标

把已验证的控制面闭环变成可复现的开发者平台：编译、工作流、评估、治理。

### 范围

- 完整化标准 YAML DSL、编译器与不可变执行快照，不在本文展开语法定义
- 简单 DAG：Agent -> 数字成果 -> Agent
- 更丰富的页面表面：查看器/编辑器、血缘图、AI 编辑
- 标签页恢复、分屏增强、看板联动和不同页面最小宽度策略
- 评估：数据集、评估器合约、发布门禁
- 治理：RBAC、策略适配器、配额、审计；Workspace 级策略对管理员可见
- OpenTelemetry 对齐与成本/延迟仪表板
- 导航按角色的管理端覆盖（仍不是客户可视化编辑器）

### 退出标准

```text
控制面配置 / DSL
 |
 v
编译器 -> ExecutionSnapshot
 |
 +----> 工作流
 +----> Agent Runtime
 +----> 评估 / 治理
 v
数字成果血缘 + 生产审计
```

## 阶段 3 - 生态系统与企业生产

### 目标

可复用的企业级 AI 生产系统与扩展生态。

### 范围

- 公开/私有/企业注册表、市场、签名、升级/回滚
- 多运行时与兼容性矩阵
- 应用平台：生成应用经 App Studio 进入工作台，支持应用展示、定制化嵌入与独立部署
- 企业治理：细粒度授权、策略即代码、密钥、合规、数据驻留
- 数字成果转换市场与完整编辑器生态
- 高可用、运行时扩展、私有云/本地打包

```text
发现 -> 安装 -> 配置 -> 评估 -> 发布 -> 部署 -> 观测 -> 治理 -> 升级/回滚
```

系统是企业级 AI 生产平台。各 Studio 仍然分工明确，但 AI 对话、应用页面、应用展示、定制化嵌入和数字成果共享同一套工作台体验，而不是各自做成互不相通的后台。

# 21. 关键架构风险与控制

| 风险                     | 为何重要                     | 控制措施                                      |
| ------------------------ | ---------------------------- | --------------------------------------------- |
| 控制面做成资源平铺后台   | 应用体验割裂                 | 领域操作全部挂入可伸缩工作台                  |
| 页面各自管理窗口状态     | 标签、菜单和上下文无法恢复   | 由控制面统一管理标签页与页面上下文            |
| 左右区域争抢页面空间     | 大页面无法有效使用           | 最小宽度声明 + 智能伸缩 + 用户偏好记忆        |
| 把 Agent/Tool/MCP 内置化 | 设置与安装流程分叉           | 统一扩展生命周期，三者都是功能扩展            |
| Workspace 漏到开发面     | 客户心智与 IAM 边界混乱      | 开发 API/控制面只暴露 Project                 |
| Project 变成新隔离键     | 与 kernel 多租户模型冲突     | 隔离仍用 tenantId+workspaceId，Project 只归属 |
| pi 内部 API 泄漏         | 基础框架升级影响产品层       | Runtime Contract + Adapter                    |
| DSL 过度投资             | 语义未定时先做编辑器         | 先实现最小执行子集和约束校验                  |
| 市场过早                 | 包合约未稳                   | 内部注册表优先                                |
| 运行时/UI 耦合           | 执行不可复现                 | ExecutionSnapshot                             |
| 数字成果仅作为文件       | 血缘、编辑和复用困难         | 独立数字成果领域模型                          |
| 扩展信任                 | 第三方代码可访问资源         | 能力 + 权限 + 沙箱                            |
| 过度微服务               | 验证阶段变慢                 | 先模块化单体                                  |

# 22. 架构决策摘要

## ADR-001 - 平台拥有执行标准

**决策：** 平台拥有领域合约、标准 YAML DSL、执行约束和不可变执行快照。
**理由：** 产品能力、权限和审计不能依赖基础框架的内部实现。

## ADR-002 - pi 作为 Agent 执行基础框架

**决策：** Agent 基于 pi 运行，通过平台适配层接收技能、工具、模型、上下文和执行约束。
**理由：** 以统一基础框架降低执行实现成本，同时由平台边界隔离 pi 版本变化。

## ADR-003 - 数字成果作为一等领域对象

**决策：** 数字成果拥有独立生命周期、版本化、血缘和转换 API。
**理由：** AI 价值通常通过持久化资产传递。

## ADR-004 - ExecutionSnapshot 作为控制/运行时边界

**决策：** 运行时执行不可变快照。  
**理由：** 可复现性、调试、审计和部署一致性。

## ADR-005 - 标准 YAML DSL 约束执行

**决策：** Agent 运行由标准 YAML DSL 描述，并在进入 pi 前编译为不可变执行快照；本文不定义 DSL 结构。
**理由：** 统一资源绑定、能力校验、权限边界、复现和审计语义。

## ADR-006 - 内部注册表优先于市场

**决策：** 先可安装包和注册表，市场后续。  
**理由：** 市场依赖稳定的清单、依赖、信任和版本化。

## ADR-007 - 先模块化单体

**决策：** 少量运行时服务，同时保持清晰模块边界。  
**理由：** 架构验证阶段降低运维复杂性。

## ADR-008 - 应用体验统一进入可伸缩工作台

**决策：** AI 对话、应用页面、应用展示、定制化嵌入和各 Studio 统一使用左侧功能区、顶部标签页、主页面、右侧看板和设置区。
**理由：** 保持能力边界的同时，为用户提供连续、可组合的应用体验。

## ADR-009 - Agent / Tool / MCP 均为功能扩展

**决策：** 基础设置只包含模型与扩展；Agent、Tools、MCP 走统一扩展安装与配置。  
**理由：** 三者共享清单、权限、生命周期和控制面贡献点；模型是运行时原语，留在基础设置。

## ADR-010 - Workspace 仅管理可见，Project 为客户开发边界

**决策：** Workspace 与 Project 都是数据归属边界；客户开发者只见 Project。隔离键仍为 `tenantId` + `workspaceId`。  
**理由：** 复用 kernel 已有隔离模型，同时给开发者一个稳定的产品入口，避免把治理空间暴露为开发容器。

## ADR-011 - 导航采用声明式调整机制

**决策：** 控制面不内置死导航。平台菜单与扩展菜单统一合并、鉴权和渲染；本文不定义其 YAML 结构。
**理由：** 调整信息架构无需修改工作台内核，并能与 console 菜单声明语义对齐。

## ADR-012 - 扩展统一贡献产品与服务能力

**决策：** 扩展可以在同一生命周期下贡献能力、菜单、页面、右侧看板、设置、接口、Agent、工具和数字成果处理器。
**理由：** 避免每类能力建立独立安装与配置机制，并保证停用、权限和审计行为一致。

# 24. 最终建议

3.2 的实施顺序：

```text
阶段 1
应用体验层 + 可伸缩工作台（功能区 / 标签页 / 主页面 / 看板 / 设置）
+ 统一扩展宿主 + Project 开发边界 + YAML DSL + pi + 数字成果
        |
        v
证明：管理空间 -> 开发项目 -> 安装扩展 -> 打开标签页 -> 对话/应用 -> 数字成果闭环
        |
        v
阶段 2
编译器 + 执行 DSL + 工作流 + 评估 + 治理
        |
        v
平台化并使执行可复现
        |
        v
阶段 3
市场 + 应用展示/嵌入 + 完整数字成果生态 + 企业运维
```

最重要的架构约束：

> **平台必须拥有合约、控制面形态和扩展生命周期；它不必拥有所有功能实现。**

最重要的产品约束：

> **客户开发者始终在 Project 与控制面中工作；Workspace 只出现在管理面。**

最重要的分层约束：

> **AI 对话、应用页面、应用展示、定制化嵌入和各 Studio 共享同一可伸缩工作台；新功能通过统一扩展贡献菜单、页面、接口、设置和右侧看板。**
