---

## 何时需要设计评审

以下情形**必须**先出方案再动手，不得边写边定：

| 情形 | 原因 |
|------|------|
| 新建 Maven 模块 | 影响依赖方向与构建拓扑 |
| 改变模块间依赖方向 | 可能造成环形依赖或层次倒挂 |
| 引入新的中间件或运行时框架 | 影响 `base` 的零中间件约束与部署形态 |
| 引入新的第三方依赖 | 需评估版本、许可证、传递依赖、安全 |
| 改动公共兼容面 | 需迁移方案 |
| 新增领域状态码或事件契约 | 涉及归属与兼容性 |
| 引入新的横切机制（缓存、鉴权、审计、多租户隔离） | 影响所有域 |
| 存储方案或表结构大改 | 需数据迁移 |

## 当前技术基线

| 维度 | 选择 | 约束 |
|------|------|------|
| JDK | 25 | `maven.compiler.release=25`，enforcer 强制 |
| 构建 | Maven ≥ 3.9.0 | 多模块 reactor + BOM + flatten |
| REST | Jakarta REST（`jakarta.ws.rs`） |端点契约禁用 Spring MVC 注解 |
| 事务 | `jakarta.transaction.Transactional` | 禁用 Spring 事务注解 |
| 持久化 | MyBatis-Plus + Jakarta Persistence 注解 | 单表、无 join、无 Mapper XML |
| 对象映射 | MapStruct + `BaseMapperConfig` | 非平凡结构转换必须使用 |
| 日志 | SLF4J + Lombok `@Slf4j` | 禁止手写 logger 字段 |
| 测试 | JUnit 5 + AssertJ + Mockito | parent 统一提供 |
| 事件 | 进程内 `EventBus` | 跨模块解耦，不改变依赖方向 |

> 本仓库管理端不使用 Spring MVC 作为端点契约；Spring / Spring Boot 专项能力见
> `java:spring`，其在本仓库的适用边界也在该技能中说明。

## 技术选型评估维度

引入新依赖或框架时逐项评估：

| 维度 | 要回答的问题 |
|------|------------|
| 必要性 | 现有 base / core 能力是否已覆盖？能否用 JDK 标准能力实现？ |
| 归属 | 业务中立（`core`）还是业务专属（业务模块 / adapter）？ |
| 依赖重量 | 传递依赖数量、是否与现有版本冲突 |
| 许可证 | 是否与项目许可证兼容 |
| 维护活跃度 | 最近发布、安全响应 |
| 约束冲突 | 是否要求 `base` 引入中间件（违反约束） |
| 版本管理 | 是否提供 BOM 以便集中管版本 |
| 兼容面 | 是否会进入 public API（若是，升级成本陡增） |
| 退出成本 | 若日后替换，影响面多大 |

结论写在架构决策记录里，并把版本登记到 `innospots-nexus-bom`。

## 常见设计陷阱

| 陷阱 | 表现 | 正确做法 |
|------|------|---------|
| 用事件绕过依赖规则 | 把具体业务事件塞进 `core`/`console` 只为让两个模块通信 | 用可同时依赖两者的 application/adapter 模块协调，或下沉真正业务中立的契约 |
| 为 mock 建接口 | 每个实现类都配一个接口 | 只有一个稳定实现时依赖具体类型 |
| 端点变业务层 | 端点里编排 DAO、写事务、做校验 | 端点只做传输，委托 service/operator |
| operator 互相依赖 | 简单数据操作层出现服务编排 | 需要协调就上提到 service |
| 跨表 join 的诱惑 | 在 DAO 写 join 或在内存做 N+1 | 分批查询 + 内存组装；跨表写交事务 service |
| 把实体当 DTO | 请求/响应直接用 `XxxEntity` | request/vo 用 record，经 MapStruct 转换 |
| 稳定键可改 | update 请求里带 `roleCode` | 稳定键创建后不可变，排除出 update |
| 状态码随意归类 | 因想要某个 HTTP 码而选类别 | 按失败语义选类别，HTTP 映射是传输层的事 |
| 空分层 | 预建 `model`/`service`/`event` 空包 | 只在有实际职责时建包 |
| 遗留结构复刻 | 照搬旧工程包结构与 POM | 遗留工程只作行为参考 |
