# 变更工作流

覆盖四类日常改动：加功能、改功能、修缺陷、重构。四类共用同一条硬约束：
**每批 Java 源文件改动后立即 `mvn clean compile`。**

---

## 通用前置：先理解再动手

无论哪类任务，动手前先回答：

| 问题 | 用途 |
|------|------|
| 这次改动属于哪个模块、哪个业务域？ | 判定归属与依赖方向 |
| 涉及哪些公共兼容面？ | 判定是否需要迁移方案 |
| 失败的语义归谁？ | 判定异常与状态码归属 |
| 现有代码里是否已有同义能力？ | 避免重复造轮子 |
| 是否有人显式要求了设计/方案？ | 决定是否需要先走 `java:design` |

回答不了就停下来问，不要猜。

## 类型一：在已有域加功能

```text
1. 定位边界     确认能力归属：endpoint / service / operator / dao / converter
2. 复用检查     搜索现有同义能力与可复用契约
3. 写测试       聚焦测试先行，确认红灯
4. 最小实现     只实现当前需要的行为，不预建分层
5. 编译门禁     mvn clean compile
6. 聚焦测试     直到转绿
7. 全量验证     交 java:check
```

### 分层落位判断

| 改动内容 | 落位 |
|---------|------|
| 新的 HTTP 入口 | `endpoint`，委托给 service 或 operator |
| 单表直接数据操作 | `operator` 的 `default` 方法或新方法 |
| 多步骤、跨 operator、跨领域、事务 | `service` |
| 结构性字段映射 | `converter`（非平凡或重复时） |
| 新失败语义 | 先搜现有状态码，必要时按九步流程扩展 |

### 加功能时容易犯的错

| 错误 | 正确做法 |
|------|---------|
| 在端点里直接写业务逻辑 | 委托 service / operator |
| 在 operator 里调用另一个 operator | 上提到 service |
| 新增 DAO 方法带 join | 单表 + 分批组装 |
| 把实体直接返回给前端 | 用 VO record + MapStruct |
| 预建 `service` 但只有一个转发方法 | 直接 `endpoint → operator → dao` |
| 为凑结构创建空包 | 只在有实际职责时建包 |

## 类型二：修改现有功能

```text
1. 确认改动范围   影响的模块、端点、表、兼容面
2. 锁定现有行为   确认有测试覆盖；没有就先补
3. 实施改动       小批量，每批后 mvn clean compile
4. 更新测试       断言反映新契约，而不是迁就实现
5. 兼容检查       是否改动公共兼容面
6. 全量验证       交 java:check
```

### 修改功能的额外检查

- 更新请求是否意外引入了不可变稳定键
- `replace` 语义是否重新定义了「省略是否删除」
- `delete` 的缺失语义是否与同资源边界内其他操作一致
- 事件载荷是否兼容既有消费者（可加字段，不得改语义）
- 状态码文案是否涉及本地化资源与告警规则

## 类型三：修复缺陷

```text
1. 复现       先写一个能复现缺陷的测试（红灯）
2. 定位       找到拥有该失败语义的边界，而不是报错的那一层
3. 修正       在正确的边界改
4. 验证       聚焦测试转绿 + 全量 mvn test
5. 回归       确认没有削弱其他测试的断言
```

### 定位原则：失败的归属边界

| 症状 | 真正该改的地方 |
|------|--------------|
| 缺参数校验导致脏数据 | 该校验规则的拥有边界（record 构造器 / `validate()` / operator / service） |
| 空指针 | 产生可空值的边界，或应归一化缺失的 operator/service，而不是在 NPE 处加判空 |
| 事务未生效 | 事务应声明的 service 方法，而不是 DAO |
| 并发下重复创建 | 稳定键与数据库/运行时唯一性，而不是加个「先查再写」 |
| 异常信息泄露内部细节 | 状态码 message/advice 与响应映射，而不是调用点 |
| 跨表数据不一致 | 事务 service，而不是 DAO |

### 禁止的「修复」方式

| 假修复 | 为什么不行 |
|--------|-----------|
| 吞掉异常返回默认值 | 隐藏失败，问题后移 |
| 放宽校验让脏数据通过 | 契约被破坏 |
| 大范围 `try-catch` 兜住 | 掩盖归属边界 |
| 加判空但语义仍错 | 症状消失，成因仍在 |
| 为让测试通过而删断言 | 测试失去价值 |
| 注释掉失败的测试 | 等同于放弃验证 |

### 修 Bug 的额外检查

- 是否需要新增状态码（**先搜现有目录**）
- 是否破坏了公共兼容面
- 同类代码是否存在相同问题（批量修要在同一变更里说清楚）
- 是否需要在行内注释里说明「为什么这样修」（解释 why）

## 类型四：重构

```text
1. 定目标       明确重构后的边界，而非"让代码好看"
2. 锁行为       用测试固定现有外部可见行为
3. 小步改       每批后 mvn clean compile
4. 守契约       公共兼容面改动必须先出迁移方案
5. 验证         全量 mvn test + java:check
```

### 重构红线

- 不得把公共兼容面的改动当作内部重构
- 不得顺手改 `nx_` 表名、稳定业务键、实体 ID 前缀、事件类型串、状态码
- 不得为了让测试通过而削弱断言
- 不得复制遗留结构来「对齐」旧工程
- 不得在重构中顺带加新功能（混在一起无法判定回归来源）

### 常见重构动作与归属

| 动作 | 说明 |
|------|------|
| 重命名类型/方法 | 若属 public 兼容面需迁移方案；遗留坏名不应仅因视觉一致而保留 |
| 提取方法/类型 | 新类型需符合命名职责后缀表 |
| 调整包结构 | 先按业务域再按职责；禁止 `impl`/`common`/`misc`/`util` |
| 消除重复 | 判定重复是同一概念还是偶然相似 |
| 拆分类 | 端点约 7 个方法触发边界复审 |
| 引入接口 | 仅在有真实边界理由时 |
| 替换工具库 | 属 `java:tool-upgrade` 范围 |

## 每批改动的收尾动作

```bash
mvn clean compile                 # 强制，不得跳过
mvn -pl <module> test             # 聚焦测试
git diff --check                  # 空白与格式问题
git status --short                # 是否有意外文件
```

全部通过后再进入下一批。全量验证（`mvn validate`、`mvn test`、
`mvn -q help:effective-pom`）交由 `java:check` 执行。

## 收尾检查清单

- [ ] 每批改动后都跑了 `mvn clean compile`
- [ ] 没有生成不能编译的代码
- [ ] 测试在实现前被观察到红灯（新功能/缺陷修复）
- [ ] 没有为让实现通过而削弱断言
- [ ] 异常在正确的边界抛出，状态码归属正确
- [ ] 没有吞掉异常、没有伪造成功数据
- [ ] 日志不含敏感值，未逐层重复记录
- [ ] 没有裸 `TODO`/`FIXME`，推迟行为有 `UnsupportedOperationException`
- [ ] public 类型与方法的 Javadoc 完整
- [ ] 行内注释解释的是 why
- [ ] 未改动公共兼容面，或已有迁移方案
- [ ] 未生成或修改模块 `SKILL.md` 与 `references/` 文档
- [ ] 已交 `java:check` 做全量验证
